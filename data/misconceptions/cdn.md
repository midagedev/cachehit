# 오개념 원장 — CDN·멀티CDN

오답 보기는 여기서 꺼내 쓴다. 원장에 없는 오해를 즉석에서 지어내지 않는다.
각 항목은 `M-<번호>`로 참조한다. 새 항목을 추가할 때는 **실제로 사람들이 그렇게 믿는 근거**(현업 대화, 블로그 오류, 스택오버플로 오답 등)를 한 줄 적는다.

---

## 헷갈리는 쌍

### M-01 캐시 미스가 나면 CDN의 의미가 사라진다
- **실제**: CDN의 이득은 두 개다. 캐시 히트(RTT 0 서빙)와 **종료점 이동**(TCP/TLS 핸드셰이크·혼잡 제어 램프업이 유저 근처 PoP에서 끝남). 미스가 나면 전자만 사라지고 후자는 그대로 남는다. 그래서 캐시 불가능한 API 트래픽에도 CDN을 붙이는 구성이 성립한다.
- **왜 믿는가**: "CDN = 캐시"라는 등식으로 배우기 때문이다. 미스 지연이 눈에 띄는 순간 캐시만 보이게 된다.
- **오답 유형**: `one-step-short`

### M-02 미드티어(tiered caching)와 origin shield는 같은 계층의 다른 이름이다
- **실제**: 미드티어는 **리전 단위로 엣지 미스를 모으는** 중간 계층이고, origin shield는 **오리진 직전의 최종 집중 캐시**다. 미스를 계층으로 모아 오리진 중복 fetch를 없앤다는 뼈대는 같지만 위치와 역할이 다르다.
- **왜 믿는가**: 벤더마다 명칭이 다르고(CloudFront Origin Shield, Fastly shielding 등) 다이어그램상 둘 다 "엣지 위의 캐시"로 그려진다.
- **오답 유형**: `adjacent`

### M-03 DNS 기반 분배와 클라이언트 사이드 분배는 구현 방식 차이일 뿐이다
- **실제**: 근본이 다르다. DNS 기반은 **전환 지연의 상한이 DNS TTL(+리졸버·스텝 캐시)**이라 제어 루프가 분 단위다. 클라이언트 사이드(플레이어의 CDN 스위처, 매니페스트 갱신)는 요청 단위로 즉시 전환한다. "즉시 페일오버"가 요구사항이면 분배 방식 자체가 갈린다.
- **왜 믿는가**: 둘 다 "트래픽을 두 CDN에 나눈다"는 결과가 같아 보인다.
- **오답 유형**: `adjacent`

### M-04 히트율이 오르면 CDN 송신(egress) 비용도 내려간다
- **실제**: CDN egress는 **전송 총량**에 비례하고 히트율과 무관하다. 히트율이 줄이는 것은 미스율(1−h)에 비례하는 **오리진 쪽 비용**(오리진 fetch·컴퓨트·오리진 egress)이다. "히트율을 올렸는데 CDN 요금이 안 줄었다"는 정상이다.
- **왜 믿는가**: "캐시가 절약해 준다"를 하나의 덩어리로 상상하기 쉽다. 요청 축과 바이트 축이 별개 과금 축이라는 사실이 직관에 없다.
- **오답 유형**: `one-step-short`

### M-05 origin shield는 켜기만 하면 PoP 수만큼의 오리진 절감이 보장된다
- **실제**: 효과는 `오리진 도달률 = 엣지 미스율 × (1−실드 히트율)`이다. 실드 히트율이 0이면 효과도 0이고, 엣지와 실드의 **캐시 키 정규화 규칙이 다르면** 실드 히트율이 깨져 계층 이득이 소멸한다. 실드 자체가 병목·장애점이 될 수 있어 이중화가 전제다.
- **왜 믿는가**: "상위 계층 하나 추가 = 중복 제거"라는 스위치 개념으로 이해하기 때문이다. 히트율이 키 규칙의 함수라는 점이 빠져 있다.
- **오답 유형**: `overgeneralized`

## 과잉 일반화

### M-06 멀티 CDN은 가용성을 거의 공짜로 올려주는 구성이다
- **실제**: 보험의 대가를 치른다 — **캐시 분할**(벤더마다 캐시가 따로 쌓여 히트율 하락, 전환 시 콜드 미스 재발)과 **운영 N벌**(무효화 API·서명 방식·로그 필드가 벤더마다 다름). 히트율 98%+ 단일 CDN, 무효화 정확성이 생명인 서비스, 협상 레버리지가 미미한 트래픽 규모에서는 이득이 비용을 못 이긴다.
- **왜 믿는가**: "벤더 두 개면 하나 죽어도 된다"는 가용성 그림만 그리기 때문이다. 비용 축(히트율·운영)은 도입 후에야 보인다.
- **오답 유형**: `overgeneralized`

### M-07 쿼리 파라미터 전체를 캐시 키에 넣는 것은 언제나 잘못된 설계다
- **실제**: 파라미터가 **변형(variant)을 정의**한다면 쿼리 전체 키가 의도된 설계다. 당근은 기본 키(쿼리 전체 포함) 위에 리사이즈 파라미터를 얹어 "값이 바뀌면 미스 → Cloud Run이 동적 리사이즈"를 의도적으로 사용한다. 진짜 위험은 변형이 아닌 파라미터(utm·추적 코드)가 키에 섞이는 것이고, 완화는 화이트리스트다.
- **왜 믿는가**: "쿼리 문자열은 캐시의 적"이라는 경구가 있다. 경구는 트래킹 파라미터 맥락에서 참이지 변형 파라미터 맥락에서는 거짓이다.
- **오답 유형**: `overgeneralized`

### M-08 CDN에서 서명을 검증하면 오리진 검증은 중복이다
- **실제**: CDN의 서명 검증은 **서명이 있을 때만 작동하는 선택적 게이트**다. 서명 파라미터가 없는 요청은 검증이 생략되어 오리진까지 관통할 수 있고(GCP Cloud CDN 공식 동작 — 당근 발표가 인용), 그 응답이 캐시될 수도 있다. 그래서 "서명된 요청은 반드시 오리진에서 검증하라"가 벤더 공식 권장이며, 만료 정책의 최종 집행자도 오리진이다.
- **왜 믿는가**: "CDN을 통과했다 = 검증받았다"로 읽히기 때문이다. 경유 자체가 필터라고 상상한다.
- **오답 유형**: `overgeneralized`

### M-09 CDN 장애 감지는 벤더 statuspage를 구독하면 충분하다
- **실제**: 실제 장애의 모습은 "벤더 전체 다운"이 아니라 **특정 리전·특정 PoP·특정 경로만 나쁜 부분 장애**다. statuspage는 늦고 불완전할 수 있다. 지역×캐시상태×오류코드로 쪼갠 자체 계측(RUM+합성)이 원본이고, 임계는 절대값보다 동일 시간대 베이스라인 대비 이탈이 노이즈에 강하다.
- **왜 믿는가**: 장애를 이진 사건(다운/정상)으로 상상하기 때문이다. 부분 장애는 전역 알럿 임계를 넘지 않아 침묵한다.
- **오답 유형**: `overgeneralized`

### M-10 캐시 용량을 늘리면 히트율이 그에 비례해 오른다
- **실제**: 웹 인기 분포는 롱테일(Zipf 계열)이라 헤드는 이미 캐시에 있고, 추가 용량이 흡수하는 꼬리는 요청당 기여가 작다. "용량 2배 = 히트율 2배"가 아니며, 용량보다 **키 정규화·화이트리스트**가 먼저다. 같은 용량에서 축출 정책 간 차이는 한 자릿수 % 포인트, 키 위생은 두 자릿수를 움직인다.
- **왜 믿는가**: 캐시를 균등 분포 상자로 상상하기 때문이다. 인기 비대칭을 넣는 순간 수익 체감 곡선이 된다는 게 안 보인다.
- **오답 유형**: `overgeneralized`

### M-11 합성(synthetic) 모니터링 점수가 좋으면 벤더를 교체해도 실사용자도 좋아진다
- **실제**: 합성은 통제된 소수 뷰포인트·조건의 재현성 있는 측정일 뿐 실사용자 분포를 대표하지 않는다. 벤더 비교의 기준값은 RUM(지역·디바이스 층화 + CDN 식별 태그 + 동시간대 비교)이어야 한다. "합성 점수로 갈았더니 실사용자는 나빠졌다"는 전형적 함정이다.
- **왜 믿는가**: 점수가 숫자로 나오고 재현성이 있어서 공정해 보인다. 측정 지점이 소수라는 사실이 숫자에 안 보인다.
- **오답 유형**: `overgeneralized`

## 직관적이지만 틀린 것

### M-12 히트율 95%에서 98%로 오르는 것은 "3%p 개선"이다
- **실제**: 오리진에 도달하는 요청은 미스율(1−h)에 비례하므로 5%→2%, 즉 **오리진 요청 60% 감소**다. 오리진이 컴퓨트(동적 리사이즈)라면 비용·안정성 축이 그 비율로 준다. 히트율 논의는 언제나 미스율과 바이트 축으로 환산해야 정확하다.
- **왜 믿는가**: 지표의 표면(3%p)이 산술의 본체(0.4배)를 가린다. 비용은 h가 아니라 1−h에 걸린다는 구조가 직관에 없다.
- **오답 유형**: `plausible-number`

### M-13 장애 시 새 CDN으로 가중치를 한 번에 반전시키는 것이 빠른 복구다
- **실제**: 전환 대상 CDN의 캐시는 비어 있다. 인기 객체 전체가 동시에 미스로 나가 오리진(컴퓨트 오리진이면 특히)에 순간 폭주한다. 정석은 점진 램프(소량→전량) + 인기 상위 워밍 + 실드·요청 병합·레이트리밋이다. 평시에도 제2벤더에 소량을 흘려 두는 웜 스탠바이가 콜드 리스크를 상시 검증한다.
- **왜 믿는가**: "장애니까 빨리 다 넘겨야 한다"는 응급 직관이 캐시가 콜드에서 시작한다는 사실을 밀어낸다.
- **오답 유형**: `one-step-short`

### M-14 DNS 가중치를 바꾸면 트래픽은 즉시 옮겨간다
- **실제**: DNS 응답이 바뀌는 것과 유저 트래픽이 바뀌는 것 사이에는 **TTL이라는 지연**이 있다. 리졸버가 TTL을 초과 절벽하는 경우까지 감안하면 수렴은 더 느리다. TTL을 낮추면 빨라지지만 DNS 조회량·권한 DNS 의존이 커진다 — 페일오버 속도와 DNS 비용의 트레이드오프다.
- **왜 믿는가**: 제어판에서 값을 바꾸는 즉시 효과를 보는 다른 설정들과 DNS를 같은 감각으로 다루기 때문이다.
- **오답 유형**: `one-step-short`

### M-15 히트율 개선의 최선은 축출 정책(LRU→LFU)을 바꾸는 것이다
- **실제**: 같은 용량에서 정책 간 히트율 차이는 보통 한 자릿수 % 포인트다. 두 자릿수를 움직이는 것은 **키 정규화**(파라미터 정렬·대소문자·화이트리스트, 쿠키 제거)다. "축출 정책 튜닝보다 키 위생이 먼저"가 실무의 우선순위다.
- **왜 믿는가**: 알고리즘 교체가 구조적 개선처럼 보인다. 정책은 캐시 안의 문제고, 키는 캐시 밖(요청이 도착하는 철자)의 문제라는 구분이 없다.
- **오답 유형**: `one-step-short`

### M-16 썸네일 같은 소 객체 서비스에서는 전송량이 비용의 전부다
- **실제**: CDN 과금은 전송량과 **요청 건당 단가**가 함께 있다. 소 객체·다 요청 트래픽(썸네일)에서는 요청 단가가 지배할 수 있다 — 이 축은 히트율과 무관하게 요청 수 자체가 입력이라, 매니페스트·목록 API 설계 같은 요청 수 구조를 봐야 한다.
- **왜 믿는가**: "용량이 작으니 전송료도 작겠지"라는 크기 직관이 건당 과금 축을 가린다.
- **오답 유형**: `one-step-short`

### M-17 원본 스토리지와 CDN의 클라우드가 달라도 비용 구조는 같다
- **실제**: 원본이 GCS인데 CDN이 AWS면 **원본→CDN 구간이 인터넷 egress로 과금**된다. 같은 클라우드 안이면 내부 처리/무료가 되는 경우가 많다(당근: Cloud Run↔Cloud Storage 트래픽 무료, 원본이 GCP라 CDN도 GCP). cross-cloud 조합은 이 구간부터 계산에 넣어야 한다.
- **왜 믿는가**: CDN 요금표만 보고 비교하면 원본 구간이 빠진다. "미스 비용"이 오리진 fetch egress까지 포함한다는 사실이 안 보인다.
- **오답 유형**: `one-step-short`

### M-18 자동 페일오버는 켤수록 좋다
- **실제**: 자동 전환은 복구 시간을 줄이지만 잘못된 신호(계측 오류·국부 장애)로 **살아 있는 벤더를 버릴 수 있다**. 실무 타협은 짧은 윈도의 다수결/지속 조건 + 점진 램프 + 자동 원상복구로 블래스트 레디어스를 제한하는 것이지 "무조건 자동"이 아니다.
- **왜 믿는가**: "자동화 = 운영 성숙"이라는 등식. 전환 자체가 새로운 사고(콜드 폭주)를 유발할 수 있다는 쪽이 안 보인다.
- **오답 유형**: `overgeneralized`

## 벤더 혼동

### M-19 서명 파라미터가 없는 요청은 CDN이 알아서 거절한다
- **실제**: GCP Cloud CDN은 서명 관련 쿼리 파라미터(Expires·KeyName·Signature)가 아예 없으면 "서명된 URL이 아니네" 하고 **검증을 건너뛴다(바이패스)**. 파라미터를 지우고 요청하면 CDN 검증 없이 오리진까지 도달하고 그 응답이 캐시될 수도 있다. "서명 안 된 요청 = 거부"는 다른 벤더의 동작 또는 상식적 기대를 Cloud CDN에 이식한 것이다.
- **왜 믿는가**: 서명 검증 기능을 켜 두면 그 게이트가 전 요청에 적용될 것이라고 읽힌다.
- **오답 유형**: `vendor-mixup`

### M-20 CDN은 오리진에 사용자가 보낸 URL을 그대로 전달한다
- **실제**: Cloud CDN은 오리진에 보낼 때 **서명 관련 쿼리 파라미터를 제거한 URL**을 보내고, 원본 URL은 `X-Client-Request-URL` 요청 헤더에 담아 전달한다. 이유는 LB의 호스트·경로 규칙이 쿼리를 포함할 수 있어(A/B 테스팅 예제) 라우팅 충돌을 예방하는 방어적 설계다. 오리진의 서명 재검증은 이 헤더를 읽어야 한다.
- **왜 믿는가**: 프록시는 URL을 보존한다는 일반 직관. 경유층이 요청을 다시 쓴다는 선택지를 상상하지 않는다.
- **오답 유형**: `vendor-mixup`

### M-21 CDN은 쿼리 파라미터의 순서·대소문자를 알아서 정규화해서 캐시한다
- **실제**: CloudFront는 파라미터의 **순서·대소문자에 따라 다르게 캐싱**한다. `?w=300&f=webp`와 `?f=webp&w=300`이 다른 캐시 엔트리가 되어 히트율이 분열한다. 당근은 서버 쪽 파라미터 생성 규칙으로 순서를 고정해서 해결했다. 정규화는 CDN이 해주는 것이 아니라 설계자가 하는 최소 위생이다.
- **왜 믿는가**: "같은 의미의 URL은 같은 것으로 봐 주겠지"라는 브라우저적 관대함을 CDN에 기대한다.
- **오답 유형**: `vendor-mixup`

### M-22 Cloud Run은 로드밸런서 백엔드에 직접 등록된다
- **실제**: Cloud Run은 LB 백엔드로 직접 붙을 수 없고 **Serverless NEG(Network Endpoint Group)** 로 매핑돼야 한다(GCP 공식 권장 — 캐싱 가능 콘텐츠를 원본으로 내리려면 부하분산기가 필요하고, Cloud Run은 서버리스 NEG로 매핑). 다른 클라우드의 "인스턴스 그룹 백엔드" 감각을 그대로 가져오면 안 되는 지점이다.
- **왜 믿는가**: LB 백엔드라는 단어가 인스턴스·서비스 직접 등록으로 읽힌다. 추상화 계층(NEG)이 다이어그램에서 작게 그려진다.
- **오답 유형**: `vendor-mixup`

## 셀프 리뷰에서 추가한 항목 (2026-08-27)

### M-23 무효화(invalidation) API를 호출하면 즉시 전역에서 사라진다
- **실제**: 무효화는 **전파에 시간이 걸리고 벤더마다 쿼터·과금이 붙는다**. 그래서 실무 교리는 무효화를 비상 수단으로 쓰고 상시 정합성은 "짧은 TTL + 버전이 바뀌는 URL"로 확보하는 것이다. 배포 직후 "캐시 무효화했는데 옛 응답이 나온다"는 지연 창의 정상 동작이다.
- **왜 믿는가**: 콘솔 버튼이 호출 즉시 200을 반환하면 전역 제거도 동기적으로 끝났다고 읽힌다.
- **오답 유형**: `one-step-short`

### M-24 캐시가 만료되면 재검증 왕복이 끝나기 전까지는 줄 것이 없다
- **실제**: `stale-while-revalidate`·`stale-if-error` 같은 지시자로 **만료된 응답을 재검증 중에(또는 오리진 장애 중에) 서빙**할 수 있다. 페일오버·오리진 장애 완화의 표준 수단이고, 무효 지연을 허용 가능한 이탈로 바꿔준다.
- **왜 믿는가**: "만료 = 못 쓴다"를 이진법으로 배운다. 오래된 것을 주는 옵션이 있다는 선택지를 상상하지 못한다.
- **오답 유형**: `one-step-short`

### M-25 Vary 헤더는 응답 메타데이터일 뿐 캐시 키와 무관하다
- **실제**: `Vary`는 **캐시 키에 사실상 축을 추가한다**. `Vary: Accept-Encoding`은 그나로 카디널리티가 작지만, 실수로 `Vary: User-Agent`·`Vary: Cookie`가 붙으면 키 공간이 유저 수만큼 분열해 히트율이 붕괴한다. 캐시 키 위생 검토의 첫 확인 항목이다.
- **왜 믿는가**: 헤더는 부가 정보라는 일반 관념. 키 공간을 정의한다는 사실이 명세 밖처럼 느껴진다.
- **오답 유형**: `adjacent`
