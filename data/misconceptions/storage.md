# 오개념 원장 — 업로드와 객체 스토리지

오답 보기는 여기서 꺼내 쓴다. 원장에 없는 오해를 즉석에서 지어내지 않는다.
각 항목은 `M-<번호>`로 참조한다. 새 항목을 추가할 때는 **실제로 사람들이 그렇게 믿는 근거**(현업 대화, 블로그 오류, 스택오버플로 오답 등)를 한 줄 적는다.

---

## 헷갈리는 쌍

### M-01 PUT presigned URL도 발급 시점에 파일 크기 상한을 강제할 수 있다
- **실제**: PUT 쿼리 서명에는 본문 크기를 강제하는 항목이 없다(페이로드 해시는 `UNSIGNED-PAYLOAD`로 남는다). 발급 시점의 크기 강제는 폼 업로드용 POST policy의 `content-length-range` 조건이 담당한다. PUT을 유지하면 크기 검증은 사후(객체 크기로 승격/거부)에 갈 수밖에 없다.
- **왜 믿는가**: presigned URL을 "서버가 서명한 요청 명세"로 상상하기 쉽고, 폼 업로드 정책의 기능을 PUT에도 있는 것으로 섞어 기억한다.
- **오답 유형**: `adjacent`

### M-02 presigned 직접 업로드로 바꿔도 서버는 업로드되는 내용을 검증할 수 있다
- **실제**: 직접 업로드에서 서버는 발급만 할 뿐 바이트를 못 지난다. 검증은 "발급 시 사전 제약 + 업로드 완료 이벤트 이후의 사후 검증 파이프라인"으로 간다. 검증의 사후화가 직접 업로드의 구조적 대가다.
- **왜 믿는가**: 서버 경유 업로드의 습관(서버가 내용을 봄)이 그대로 남는다. 발급 API가 검사한 값이 실제 올라오는 바이트와 같을 거라고 가정한다.
- **오답 유형**: `one-step-short`

### M-03 클라이언트 완료 콜백을 업로드 완료의 진실로 삼아도 된다
- **실제**: 클라이언트는 실패하면 콜백을 안 보내고(앱 종료, 네트워크 단절), 안 됐는데 됐다고 보낼 수도 있으며, 재시도하면 중복으로 보낸다. 진실의 원천은 스토리지 이벤트(S3 이벤트 알림, GCS `OBJECT_FINALIZE`)고 콜백은 UX 힌트다.
- **왜 믿는가**: 콜백이 오는 경우가 대부분이라, 예외가 구조적이라는 걸 데이터로 겪어보기 전까지는 보이지 않는다.
- **오답 유형**: `one-step-short`

### M-04 multipart로 올린 객체의 ETag도 MD5라 무결성 검증에 쓸 수 있다
- **실제**: 단발 PUT의 ETag는 MD5지만 multipart의 ETag는 파트 수와 파트별 해시로 만든 별도 값이다. 무결성 검증은 `x-amz-checksum-*` 계열이나 파트별 검증으로 한다. GCS는 md5Hash/crc32c를 메타데이터에 기본 계산해 둔다.
- **왜 믿는가**: "ETag = MD5"를 단발 PUT 경험에서 일반화한다. 검증 실패를 클라이언트 계산 탓으로 돌려 원인 파악이 늦어진다.
- **오답 유형**: `overgeneralized`

### M-05 SSE-KMS는 SSE-S3의 순수 상위 호환이다
- **실제**: 키 통제와 감사는 강해지지만, 객체 GET마다 KMS 복호화 요청이 따라붙어 요청당 과금과 스로틀이라는 새로운 축이 생긴다. 읽기가 뜨거운 CDN 오리진에서는 암호화 정책 하나가 비용 구조를 바꾼다.
- **왜 믿는가**: "더 강한 암호화 = 더 좋은 옵션"이라는 직관. 요금이 저장 축이 아니라 요청 축에 붙는다는 걸 청구서에서 처음 발견한다.
- **오답 유형**: `one-step-short`

### M-06 presigned URL은 한 번 쓰면 소멸한다
- **실제**: 만료 전까지 소지자 누구나 몇 번이고 실행할 수 있다(1회성 토큰이 아니다). 그래서 키는 난수로 지정해 재사용·덮어쓰기가 무해하게 만들고, 소유권은 사후 검증으로 확정한다.
- **왜 믿는가**: 서명 URL을 OTP 같은 일회용 코드로 상상한다. "발급, 사용, 만료"로 흘러가는 UX가 그렇게 느끼게 한다.
- **오답 유형**: `adjacent`

### M-07 스토리지 PUT보다 DB 커밋을 먼저 하는 편이 안전하다
- **실제**: 반대다. 먼저 커밋하면 "DB에는 있는데 객체가 없는" 역방향 불일치가 양산된다(서비스 가능 레코드가 404). 기본 순서는 PENDING 레코드, 스토리지 PUT, 이벤트 확정 순이고 실패는 보상 삭제로 정리한다.
- **왜 믿는가**: "레코드가 있으면 객체를 나중에 채우면 된다"는 RDB 관성. 역방향 실패가 사용자에게 깨진 이미지로 먼저 보인다는 점을 간과한다.
- **오답 유형**: `inverted`

## 시대가 지난 것

### M-08 S3는 eventual consistency라 PUT 직후 GET이 옛 값을 돌려줄 수 있다
- **실제**: 2020년 12월 1일부터 신규 객체 PUT/DELETE를 포함해 강한(read-after-write) 일관성이다. "PUT 직후 GET 실패 대비 재시도"는 구식 조언이고, GCS는 출시부터 강한 일관성이었다.
- **왜 믿는가**: 2020년 이전의 문서와 블로그가 여전히 검색 결과 상단에 있다. "분산 시스템이라 어쩔 수 없다"는 통념과도 맞물린다.
- **오답 유형**: `outdated`

### M-09 핫스팟을 피하려면 키 프리픽스를 해시로 흩뿌려야 한다
- **실제**: 2018년 7월 이후 S3는 프리픽스당 초당 최소 3,500 PUT / 5,500 GET을 자동 확장한다. 랜덤 프리픽스 권고는 철회됐고, 키 설계는 가독성·리스팅·권한 경계 중심으로 하면 된다.
- **왜 믿는가**: 옛 성능 지침이 담긴 발표 자료와 블로그가 아직 돈다. "샤딩하면 안전하다"는 직관이 겹쳐진다.
- **오답 유형**: `outdated`

### M-10 CloudFront로 S3 원본을 지키는 현재 방식은 OAI다
- **실제**: OAI(Origin Access Identity)는 레거시고, 2022년 도입된 OAC(Origin Access Control)가 대체 권장이다. OAC는 모든 오리진 메서드와 SSE-KMS로 암호화된 객체 접근까지 지원한다.
- **왜 믿는가**: OAI로 동작하는 튜토리얼이 너무 많고, "이미 잠겨 있다"고 믿는 설정은 다시 읽지 않는다.
- **오답 유형**: `outdated`

## 과잉 일반화

### M-11 저렴한 스토리지 클래스로 내리면 비용은 줄어든다
- **실제**: 저장 단가만 낮아질 뿐 조회(GB당) 수수료와 최소 보관 기간이 얹히고, 요청 단가와 전환 요청료도 클래스마다 다르다. "가끔 읽는다"가 아니라 "안 읽는다"를 확신할 때만 내린다.
- **왜 믿는가**: "스토리지 비용 = GB당 저장료"라는 단일 축 모델. 청구서를 항목별로 갈라보는 습관이 없으면 조회 수수료가 보이지 않는다.
- **오답 유형**: `overgeneralized`

### M-12 스토리지가 강한 일관성이면 서빙 파이프라인 전체가 일관적이다
- **실제**: 강한 일관성은 리전 내 객체 스토리지의 이야기다. CDN 캐시(TTL까지 옛 값), 크로스리전 복제(비동기), 버킷 정책 전파는 여전히 별도의 지연 계층이다.
- **왜 믿는가**: "S3가 일관적이라 바로 보인다"가 "전체가 바로 보인다"로 확장된다. 지연의 원인이 주변 계층에 있을 때 스토리지부터 의심하게 된다.
- **오답 유형**: `overgeneralized`

### M-13 추측 어려운 키 이름이면 공개 버킷도 안전하다
- **실제**: 키 비밀성은 접근 통제가 아니다. 리퍼러, 클라이언트 로그, 리스팅 버그, 공유로 키는 새고 공개 버킷은 열람 사고의 1순위 원인이다. 버킷은 잠그고(CDN 서비스 주체만 신뢰) 사용자는 서명 URL로 통제한다.
- **왜 믿는가**: UUID가 사실상 비밀번호처럼 보인다. 사고가 나기 전까지는 "운으로 버티는 설정"이 설계로 느껴지지 않는다.
- **오답 유형**: `overgeneralized`

### M-14 같은 키에 PUT하면 객체가 부분 수정된다
- **실제**: 부분 갱신은 없다. PUT은 객체를 통째로 교체하고, 버전 관리가 켜져 있으면 이전 버전이 남는다. 메타데이터 변경조차 복사 후 교체(리라이트)다.
- **왜 믿는가**: 파일 시스템의 in-place 수정 모델을 그대로 가져온다. "수정"과 "교체"의 비용 차이를 청구서에서 처음 발견한다.
- **오답 유형**: `overgeneralized`

### M-15 버킷 리스팅 순회로 DB와 동기화할 수 있다
- **실제**: LIST는 페이지당 1,000키 순회다. 수억 키 버킷의 전체 순회는 요청·시간 폭탄이고, 리스팅에는 진행 중인 multipart 세션도 보이지 않는다. 대규모 정합성은 인벤토리(매니페스트)나 날짜 파티션 diff로 한다.
- **왜 믿는가**: 파일 시스템 glob이나 디렉터리 스캔의 비용 감각을 그대로 옮긴다.
- **오답 유형**: `overgeneralized`

### M-16 presigned URL의 만료는 필요한 만큼 길게 잡을 수 있다
- **실제**: AWS SigV4 쿼리 서명과 GCS V4 서명 모두 만료 상한이 7일(604800초)이다. 긴 유효기간이 필요하면 재발급 흐름을 설계해야지 URL을 길게 못 낸다. 실무 권장은 목적별 짧은 만료(업로드는 분 단위)다.
- **왜 믿는가**: 상한에 부딪히기 전까지는 문서의 해당 절을 안 읽는다. "서명이면 기간도 자유"라고 가정한다.
- **오답 유형**: `overgeneralized`

### M-17 만료와 발급 창을 조이면 업로드 남용 전반이 통제된다
- **실제**: 짧은 만료와 발급 레이트리밋이 통제하는 것은 "언제, 누가, 몇 번"이다. "무엇이"(내용, 크기)는 발급 시 사전 제약(POST policy)이나 사후 검증 없이는 통제되지 않는다.
- **왜 믿는가**: 시간축 통제는 눈에 잘 보이고 내용축 검증은 파이프라인이라 무겁게 느껴진다.
- **오답 유형**: `overgeneralized`

### M-18 발급 API가 인증돼 있으면 URL 실행 시에도 자격 검증이 따라온다
- **실제**: presigned URL 검증은 "누가"가 아니라 "URL과 서명이 유효한가"만 본다. 만료 전까지는 발급 맥락(그 사용자, 그 세션)과 무관하게 실행된다. 발급 인가와 실행 인가는 다른 층이다.
- **왜 믿는가**: "인증된 경로에서 나온 링크"라서 보호되어 있다고 직관한다. URL이 소지 기반(bearer)이라는 사실이 반직관적이다.
- **오답 유형**: `overgeneralized`

### M-19 Autoclass는 접근 패턴과 무관하게 비용을 절감한다
- **실제**: Autoclass의 클래스 전환에는 조회 수수료와 최소 보관 기간이 붙지 않는 대신 객체당 모니터링 요금(1,000개 단위 과금)이 얹힌다. 전량 항상 뜨거운 버킷이나 초소형 객체 다발에서는 순수 Standard나 명시적 lifecycle 규칙이 더 싸다. 접근 패턴을 모르는 혼성 원본 저장소에 가장 잘 맞는다.
- **왜 믿는가**: "매니지드 자동 최적화"라는 이름. 절감이 저장 단가 축에서만 일어난다고 가정한다.
- **오답 유형**: `overgeneralized`

## 직관적이지만 틀린 것

### M-20 완료·중단되지 않은 multipart 파트는 과금되지 않는다
- **실제**: Complete도 Abort도 하지 않은 파트는 버킷에 남아 저장료가 붙는다. 클라이언트가 비정상 종료하면 중단 요청 자체를 못 보낸다. 그래서 AbortIncompleteMultipartUpload lifecycle 규칙이 장식이 아니라 필수다.
- **왜 믿는가**: "실패한 업로드는 안 남는다"는 직관. 미완료 파트는 콘솔의 객체 목록에도 안 보여 눈으로 확인되지 않는다.
- **오답 유형**: `overgeneralized`

### M-21 multipart 파트 크기에는 최소가 없다
- **실제**: 마지막 파트를 제외한 각 파트는 최소 5MB다. 작게 쪼개면 UploadPart는 성공해도 CompleteMultipartUpload가 EntityTooSmall로 거부한다. 이 최소는 재전송 단위 설계의 출발점이 된다(관례상 파트당 5MB에서 수십 MB).
- **왜 믿는가**: "작은 파트 = 더 빠른 재시도"라는 상식이 제약과 충돌하는 걸 오류를 만나고 나야 안다.
- **오답 유형**: `plausible-number`

### M-22 객체를 지우거나 만료시키면 과금은 그 즉시 멈춘다
- **실제**: 버전 관리 버킷의 DELETE는 삭제 마커일 뿐 비현행 버전이 남아 저장료가 계속되고, IA 이하 클래스는 최소 보관 기간의 잔여분을 물고 나간다. 절감은 만료 규칙(비현행 버전 정리 포함)과 함께 설계해야 한다.
- **왜 믿는가**: "없으면 공짜"라는 물리적 직관. 삭제가 상태 전환이자 청구 이벤트라는 걸 청구서에서 발견한다.
- **오답 유형**: `one-step-short`

### M-23 콘텐츠 해시를 키로 쓰면 이득만 있고 대가는 없다
- **실제**: dedup, 무결성, 불변 캐싱은 공짜로 따라오지만 삭제는 참조 계산이나 mark-and-sweep GC가 필요해지고, 접근 권한은 키와 분리된 계층(DB와 서명 URL 발급)에서만 판정 가능해진다. 개인정보성 콘텐츠는 dedup를 포기하는 판단도 있다.
- **왜 믿는가**: 해시 키의 장점은 소개로 먼저 도착하고 운영(삭제, 권한)의 복잡도는 나중에 도착한다.
- **오답 유형**: `one-step-short`

### M-24 비즈니스 상태는 객체의 커스텀 메타데이터에 둬도 관리가 된다
- **실제**: 객체 메타데이터 갱신은 복사 후 교체(전체 리라이트)라 자주 바뀌는 상태에 어울리지 않고 질의(필터, 조인)도 못 한다. 교체는 ObjectCreated 이벤트를 다시 발화해 파이프라인까지 재가동시킨다. SSOT는 DB고 커스텀 메타는 디버깅 힌트다.
- **왜 믿는가**: "스토리지에도 메타데이터가 있으니 DB를 줄일 수 있다"는 절약 직관.
- **오답 유형**: `one-step-short`

### M-25 키를 회전하면 기존 객체도 새 키로 재암호화된다
- **실제**: 회전은 새 쓰기에 새 키 버전을 쓸 뿐, 기존 객체는 구버전 키로 복호화만 된다(키 버전 보존이 전제다). 회전 비용 걱정으로 회전을 미루는 건 잘못된 계산이다.
- **왜 믿는가**: "돌린다"는 동사가 전체 재작업으로 그려진다. 실제 메커니즘(키 버전 참조)은 문서를 읽어야 나온다.
- **오답 유형**: `inverted`

## 벤더 혼동

### M-26 재개 가능 업로드는 GCS에만 있고 S3에는 없다
- **실제**: 이름은 다르지만 S3에도 있다. multipart upload가 파트 단위 재개를 담당한다(개념 대응: GCS 세션 URI가 S3 uploadId에 해당). GCS resumable은 오프셋 조회로 청크를 이어 올린다. 재개 가능 업로드를 자체 포맷으로 재발명하지 않는다(자체 서버 경유가 필요하면 tus 같은 공개 프로토콜이 있다).
- **왜 믿는가**: GCS 문서는 "resumable"이라는 이름으로 기능을 부각하는데 S3는 multipart 설명 안에 재개성이 숨어 있다.
- **오답 유형**: `vendor-mixup`

### M-27 GCS는 체크섬을 클라이언트가 직접 계산·보관해야 한다
- **실제**: GCS는 모든 객체의 메타데이터에 md5Hash와 crc32c를 서버가 기본 계산해 저장한다(합성 객체는 crc32c). S3는 요청에 실어야 검증하는 구조(Content-MD5, x-amz-checksum-*)다. S3 워크플로를 GCS에 이식하면 쓸데없는 별도 보관 체계를 만들게 된다.
- **왜 믿는가**: S3 워크플로(클라이언트가 MD5를 계산해 첨부)를 표준인 양 가져온다.
- **오답 유형**: `vendor-mixup`

## 셀프 리뷰에서 추가한 항목

초안 원장(M-01~M-27)을 다시 훑으며 "실무자가 실제로 헷갈리는데 빠졌다"고 판정해 추가한 항목이다.

### M-28 스토리지 이벤트 알림은 정확히 한 번 전달된다
- **실제**: 이벤트 경로(S3 알림에서 SQS/SNS/Lambda로, GCS에서 Pub/Sub으로)는 적어도 한 번(at-least-once) 전달을 전제한다. 중복·재전달은 정상 동작 범위고 소비 쪽은 멱등한 조건부 상태 전이로 흡수해야 한다.
- **왜 믿는가**: "알림"이라는 단어가 정확히 한 번처럼 들린다. 중복 이벤트는 장애일 때만 나오는 걸로 가정한다.
- **오답 유형**: `overgeneralized`

### M-29 버전 관리 버킷에서 DELETE를 하면 이전 버전까지 즉시 지워진다
- **실제**: DELETE는 삭제 마커를 남기는 소프트 삭제다. 과거 버전은 그대로(과금도 그대로) 남고, 특정 버전을 명시해 지워야 영구 삭제다. 이 비대칭이 운영자 실수 복구의 기본 방어선이자 "지웠는데 비용이 안 내려간다"는 함정이기도 하다.
- **왜 믿는가**: DELETE라는 동사의 일상적 의미. 콘솔에서 지우면 목록에서 사라져서 "갔다"고 느낀다.
- **오답 유형**: `one-step-short`

### M-30 같은 리전 안의 스토리지 트래픽은 경로와 무관하게 무료다
- **실제**: 무료가 되는 조건은 경로에 있다. 프라이빗 서브넷의 워크로드가 NAT 게이트웨이를 거쳐 스토리지 공용 엔드포인트에 닿으면 NAT 처리량 과금이 붙는다. 게이트웨이 VPC 엔드포인트(S3)나 Private Service Connect로 직결하는 것이 비용 정석이다.
- **왜 믿는가**: "같은 리전은 무료"라는 요약이 경로 조건 없이 회자된다.
- **오답 유형**: `overgeneralized`

## 이벤트·복제·수명주기 (2026-08-27 storage 확장 라운드)

### M-31 복제 규칙은 켜는 순간 기존 객체도 소급 복제된다
- **실제**: 라이브 복제는 규칙 생성 이후 쓰이는 객체만 옮긴다. 그 전부터 있던 객체는 배치 복제(S3 Batch Replication) 같은 주문형 작업으로 별도 옮겨야 한다.
- **왜 믿는가**: "복제 = 버킷 동기화"라는 이미지. 설정 직후 목적지가 비어 있으면 "아직 오는 중"으로 읽는다. CRR을 켠 뒤 목적지가 비어 있다는 실무 문의가 반복된다.
- **오답 유형**: `overgeneralized`

### M-32 복제로 목적지에 도착한 객체는 이벤트를 발화하지 않는다
- **실제**: 복제 쓰기도 목적지 버킷 입장에서는 새 객체 생성이라 ObjectCreated:Put으로 발화된다. ObjectCreated에는 복제본 표시 필드가 없고(Replication:* 이벤트는 원본 쪽 실패·임계 지표용) 양쪽 버킷에 알림을 걸면 평시에도 이중 처리가 일어난다.
- **왜 믿는가**: 복제를 "스토리지 내부 이동"으로 상상해 목적지에서는 새 쓰기가 아닌 걸로 본다. 표시 필드가 있을 거라고 덧붙여 믿기도 한다.
- **오답 유형**: `inverted`

### M-33 이벤트 알림은 발생한 순서대로 도착한다
- **실제**: 순서는 보장되지 않는다. 같은 키의 PUT/DELETE 이벤트에는 sequencer 값이 실려 있어 소비 쪽에서 이 값으로 선후를 판정해야 한다.
- **왜 믿는가**: 큐가 시간순으로 쌓인다는 직관. 역순 도착은 장애일 때만 나오는 걸로 가정한다.
- **오답 유형**: `overgeneralized`

### M-34 TCP가 체크섬을 하니 전송 중 손상은 걸러진다
- **실제**: TCP 체크섬은 16비트 약검사라 우연히 통과하는 손상이 있고 전 경로(메모리, 프록시, 디스크)를 덮지도 않는다. 종단 간 보장은 업로드에 x-amz-checksum 계열(CRC32, CRC32C, SHA-1, SHA-256)을 실어 서버가 검증하고 다운로드 시 같은 값을 회수해 비교해야 얻는다. Content-MD5는 레거시다.
- **왜 믿는가**: 손상이 극히 드물어 "전송 구간은 안전하다"는 직관이 자란다. 깨진 파일이 나오면 양 끝 저장 장치부터 의심한다.
- **오답 유형**: `overgeneralized`

### M-35 서버 액세스 로그는 완전하고 즉시다
- **실제**: 최선형(best-effort) 전달이다. 대부분 수 시간 내 오지만 더 늦을 수 있고 아예 안 올 수도 있으며 중복도 있다. 문서가 직접 "완전한 청구·감사 기록용이 아니다"라고 못박는다. 객체 레벨 감사는 CloudTrail 데이터 이벤트가 맡는다.
- **왜 믿는가**: "로그"라는 이름과 대시보드의 평소 정상적인 모습. 결측이 보이면 수집기 버그부터 의심한다.
- **오답 유형**: `overgeneralized`

### M-36 presigned URL의 서명은 경로와 만료에만 걸리고 헤더는 자유다
- **실제**: 서명 범위(signed headers)에 들어간 헤더는 요청에 같은 값으로 실려야 한다. 발급 시 Content-Type이 서명에 포함됐는데 다른 값으로 보내면 SignatureDoesNotMatch가 난다.
- **왜 믿는가**: URL이니 "주소"만 서명된다고 상상한다. 403이 나면 CORS부터 의심하는 문의가 반복된다.
- **오답 유형**: `overgeneralized`

### M-37 발급된 presigned URL은 만료 전에 회수할 수 있다
- **실제**: URL을 폐기하는 수단은 없다. 서명에 쓰인 자격 증명이 비활성화·삭제되면 그보다 늦은 만료라도 무효가 되는데, 사후 차단은 이 축에서만 된다.
- **왜 믿는가**: OTP의 발급·사용·폐기 모델을 겹쳐 본다. 사고가 나면 "URL을 지워달라"고 요청하게 된다.
- **오답 유형**: `adjacent`

### M-38 수명주기 전이 규칙은 모든 객체에 적용된다
- **실제**: 전이는 기본 동작으로 128KB 미만 객체를 대상에서 제외한다(2024년 9월부터 기본, 크기 필터로 명시적으로 풀 수 있다). 작은 객체 위주 버킷에서는 규칙이 성공 상태여도 아무 것도 내려가지 않는다. 참고로 IA 계열은 128KB가 최소 과금 단위라 작은 객체를 내릴 이득 자체가 없다.
- **왜 믿는가**: 규칙은 버킷 단위 정책이니 모든 객체에 균일하게 적용된다고 읽는다. 비용이 안 내려가면 규칙 상태부터 의심한다.
- **오답 유형**: `overgeneralized`

### M-39 지운 객체는 한동안 보관 창이 있어 기한 내 복구된다
- **실제**: 휴지통이나 보관 창은 없다. 버전 관리가 켜져 있으면 삭제 마커 제거로, 꺼져 있으면 회수 수단이 없다. "30일 후 자동 청소 전에 복구" 같은 창도 없다.
- **왜 믿는가**: OS 휴지통과 일부 관리형 삭제 정책이 겹쳐 기억된다. "지운 지 30일 안이면 복구되죠"라는 문의가 실제로 온다.
- **오답 유형**: `plausible-number`

### M-40 버전 관리를 일시중단하면 지금의 삭제가 되돌려진다
- **실제**: 일시중단은 새 쓰기에 버전을 못 붙이게 할 뿐 이미 남은 삭제 마커나 버전을 건드리지 않는다. 되돌리기는 마커의 버전 ID를 지정해 지우는 별도 작업이다.
- **왜 믿는가**: "버전 관리를 끄면 버전이 풀린다"는 토글 상상. 콘솔의 상태 표시가 토글처럼 생겼다.
- **오답 유형**: `adjacent`

### M-41 GCS Pub/Sub 알림은 중복 없이 정확히 한 번 온다
- **실제**: Pub/Sub 기본 전달도 적어도 한 번이다. 정확히 한 번은 구독별 옵션 기능이고 알림 기본값이 아니다. S3만의 제약이 아니라 이벤트 경로의 일반적 계약이다.
- **왜 믿는가**: 벤더 비교 글의 "정확히 한 번 지원" 문구를 알림 기본값으로 읽는다.
- **오답 유형**: `vendor-mixup`

### M-42 이벤트 발화에는 초당 상한이 있어 초과분은 드랍된다
- **실제**: 알림 경로에 그런 드랍 상한은 문서화돼 있지 않다. 초당 3,500/5,500은 요청 처리량 이야기고 알림의 계약은 적어도 한 번 전달이다.
- **왜 믿는가**: 요청 상한 숫자가 이벤트에도 있는 걸로 혼합된다. 빠진 이벤트를 처리량 한도로 설명하려 한다.
- **오답 유형**: `plausible-number`

## 2024~2026 자료 수집 라운드에서 추가 (2026-08-28)

### M-43 S3에서 읽고-계산-쓰기 경쟁은 외부 락 없이는 못 막는다
- **실제**: 2024년부터 조건부 쓰기가 원시 기능이다. If-Match(ETag)로 compare-and-swap, If-None-Match: * 로 write-once가 되고, 실패는 412(경합 중 409 선행 가능)로 돌아온다. 락 서비스 없이 다중 쓰기 조정이 가능하다.
- **왜 믿는가**: S3를 '조건 없는 마지막 쓰기 승리' 저장소로 배운 시절의 지식이 굳어 있다.
- **오답 유형**: `outdated`

### M-44 Intelligent-Tiering에 두면 찬 데이터는 알아서 아카이브 요금이 된다
- **실제**: 자동 계층화는 접근 즉시 빈번 접근 계층으로 되돌린다. 드물어도 산발 조회가 이어지는 데이터는 저렴한 계층에 머물지 못한다. 접근이 확실히 드물고 패턴이 알려져 있다면 수명주기 고정 전이가 더 싸다.
- **왜 믿는가**: '자동'이라는 말에서 최적 배치를 기대하고, 승격 규칙(접근 1회 = 즉시 승격)을 모른다.
- **오답 유형**: `adjacent`

### M-45 버전 관리가 꺼진 버킷에서 삭제하면 복구 수단이 없다
- **실제**: GCS soft delete는 버전 관리와 별개의 기본 활성 안전망으로, 삭제 객체를 기본 7일간 보존해 복원할 수 있다. 대가로 보존 중 저장 요금이 나가므로 임시 버킷은 꺼 두라는 것이 공식 권고다.
- **왜 믿는가**: S3의 모델(버전 관리+삭제 마커가 유일한 안전망)을 GCS에 그대로 이식한다.
- **오답 유형**: `vendor-mixup`
